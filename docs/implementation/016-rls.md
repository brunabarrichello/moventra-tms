# 016 — RLS / Defesa adicional

## Estado

`ACTIVE / BATCH 012–017`

Production permanece deferida até a 017.

## Decisão

RLS é defesa em profundidade e não substitui Membership, RBAC, escopo organizacional ou autorização de domínio no backend.

O Tenant efetivo é definido somente dentro de transação por:

```text
set_config('moventra.tenant_id', tenant_uuid, true)
```

O terceiro argumento `true` mantém o valor transaction-local e evita vazamento de contexto entre conexões reutilizadas pelo pool.

## Tabelas protegidas

- `organization.tenants`;
- `organization.companies`;
- `organization.branches`;
- `identity.memberships`;
- `security.roles`;
- `security.role_permissions`;
- `security.membership_roles`;
- `security.organizational_scopes`;
- `security.role_assignment_scopes`.

Entidades globais `identity.users`, `identity.external_identities` e `security.permissions` não recebem RLS tenant-based.

## Segurança

- contexto é validado como UUID canônico;
- query sem contexto não deve enxergar linhas tenant-scoped para roles sujeitas a RLS;
- policy protege leitura e escrita (`USING` + `WITH CHECK`);
- `FORCE RLS` não é habilitado nesta fase para não interferir no owner/migration path;
- runtime deve operar com role least-privilege não proprietária;
- UUID informado por cliente não é usado diretamente como contexto sem autorização prévia.

## Gate técnico

Migration/validation PostgreSQL 18, helper transacional, testes de catálogo/boundary e CI verdes, depois Neon Staging. Evidência Production e conclusão formal ficam para o encerramento do batch na 017.
