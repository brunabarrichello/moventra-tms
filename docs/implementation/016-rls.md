# 016 — RLS / Defesa adicional

## Estado

`CONCLUDED`

Concluída no fechamento conjunto do batch 012–017 após promoção Production protegida da revisão funcional final.

## Decisão

RLS é defesa em profundidade e não substitui Membership, RBAC, escopo organizacional ou autorização de domínio no backend.

O Tenant efetivo é definido dentro da transação por contexto autorizado:

```text
set_config('moventra.tenant_id', tenant_uuid, true)
```

O terceiro argumento `true` mantém o valor transaction-local e evita vazamento de contexto entre conexões reutilizadas pelo pool.

## Tabelas protegidas

- `organization.tenants`;
- `organization.companies`;
- `organization.branches`;
- `identity.memberships`;
- `security.roles`;
- `security.role_permissions`;
- `security.membership_roles`;
- `security.organizational_scopes`;
- `security.role_assignment_scopes`.

Com a fase 017, `audit.audit_events` também possui RLS tenant-aware. Entidades globais `identity.users`, `identity.external_identities` e `security.permissions` permanecem sem RLS tenant-based.

## Segurança

- contexto é validado como UUID canônico e vem da autorização efetiva, não de input não confiável;
- policies protegem leitura e escrita com `USING` + `WITH CHECK`;
- runtime deve usar role least-privilege não proprietária;
- `FORCE RLS` permanece fora deste contrato para preservar paths administrativos/migrations explicitamente controlados;
- autorização backend continua obrigatória mesmo quando RLS está ativo.
