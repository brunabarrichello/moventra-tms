## Objetivo

Introduzir um subsistema transversal de **Dead Letter / Quarentena** para falhas terminais de mensageria e Jobs, com persistência durável, isolamento tenant, governança, auditoria e reprocessamento idempotente.

DLQ no Moventra não é apenas uma queue física do RabbitMQ. O broker pode transportar mensagens dead-letter, porém a fonte operacional auditável deve ser provider-neutral e durável.

## Princípios

```text
provider-neutral na aplicação
+
RabbitMQ DLX/DLQ como adapter de transporte
+
PostgreSQL como registro operacional durável
+
reprocessamento idempotente
+
RBAC + RLS + Audit no backend
+
sem edição arbitrária de payload
+
sem loop infinito de redelivery
```

A garantia continua **at-least-once**. A fase 026 não cria exactly-once fim a fim.

## Escopos físicos

A convenção 007 continua obrigatória: tabela tenant-scoped não usa `tenant_id NULL` para representar registros globais.

Modelo recomendado:

```text
dlq.entries
  = falhas pertencentes a tenant
  = tenant_id UUID NOT NULL
  = RLS obrigatório


dlq.system_entries
  = falhas técnicas/globais da plataforma
  = sem tenant_id
  = acessíveis somente por capability interna/role administrativa autorizada
```

Não misturar os dois escopos em uma única tabela nullable.

## Fontes de entrada

A DLQ deve suportar inicialmente:

1. **mensageria** — mensagem rejeitada/não recuperável ou tentativas esgotadas;
2. **jobs** — `failed_terminal` quando o handler/job estiver catalogado para quarentena;
3. futuras integrações podem registrar falhas usando o mesmo contrato, sem acoplar domínio ao RabbitMQ.

Uma entrada deve indicar uma origem controlada:

```text
source_kind = message | job
```

Outros valores somente após mudança versionada do catálogo.

O snapshot não é um dump irrestrito do erro. Ele deve conter somente dados allowlisted necessários para reprocessar de forma segura.

### Unicidade

Uma mesma ocorrência lógica não pode gerar entradas concorrentes duplicadas:

```text
UNIQUE (tenant_id, source_kind, source_id)
```

para tenant e:

```text
UNIQUE (source_kind, source_id)
```

para system.

Quando a origem admite múltiplos ciclos independentes de quarentena, a chave deverá incluir uma geração/cycle id explícita e controlada, nunca timestamp arbitrário para contornar dedupe.

## State machine

```text
quarantined
   ├── request reprocess ──→ reprocess_pending
   │                            │
   │                            ▼
   │                       reprocessing
   │                         ├── success ──→ resolved
   │                         └── failure ──→ quarantined
   │                                      ou exhausted
   │
   ├── acknowledge ────────→ resolved
   └── discard ────────────→ discarded

exhausted = terminal para reprocessamento automático/manual normal
```

Estados canônicos iniciais:

```text
quarantined
reprocess_pending
reprocessing
resolved
discarded
exhausted
```

Transições devem ser condicionais e concorrência-safe. Nenhuma API pode fazer update livre de `status`.

## Reprocessamento

### Regras

- reprocessamento é **uma nova tentativa controlada**, não mutação do registro original;
- o operador não pode editar `snapshot`, event type, tenant, handler ou routing key;
- toda solicitação usa chave idempotente;
- duas solicitações concorrentes não podem produzir dois efeitos lógicos;
- `max_reprocess_attempts` é bounded por configuração confiável;
- aplicar cooldown/backoff antes de nova tentativa quando necessário;
- `resolved` e `discarded` não voltam para quarentena sem uma nova ocorrência de origem válida;
- `exhausted` exige ação excepcional futura governada, não retry infinito.

### Mensagem

Para uma entrada `source_kind=message`:

```text
claim DLQ entry
→ reconstruir MessageEnvelope somente a partir do snapshot validado
→ publicar no exchange canônico via MessagingPublisher
→ publisher confirm
→ marcar DLQ resolved
```

O `messageId/eventId` de dedupe deve permanecer estável quando representar a mesma intenção lógica. Se o contrato exigir um identificador de tentativa separado, ele fica em metadata controlada, não substitui a identidade lógica.

### Job

Para uma entrada `source_kind=job`:

```text
claim DLQ entry
→ validar job_type/schema_version no JobHandlerRegistry
→ reschedule/retry por capability de Jobs
→ persistir vínculo da nova tentativa
→ marcar DLQ resolved somente após aceite transacional da nova execução
```

Não permitir `eval`, import dinâmico ou handler informado pelo operador.

## RabbitMQ DLX/DLQ

A fase 024 já suporta configuração de `x-dead-letter-exchange` no adapter de consumo. A 026 deve completar o contrato operacional:

```text
primary exchange/queue
      │ nack(requeue=false)
      ▼
dead-letter exchange
      ▼
dead-letter queue
      ▼
DLQ ingestion adapter
      ▼
PostgreSQL dlq.*
```

Regras:

- exchanges/queues durable;
- nomes provenientes de configuração/catalogo confiável;
- bindings explícitos;
- mensagens persistentes;
- `prefetch` bounded;
- manual ack;
- a mensagem da dead-letter queue só recebe ack após a entrada durável da DLQ ser confirmada;
- falha temporária ao persistir a entrada deve manter a mensagem recuperável;
- poison message inválida deve ser tratada sem loop infinito;
- headers `x-death` são metadados do broker, nunca fonte confiável de Tenant/autorização.

## Captura de falhas de Jobs

A 025 possui `failed_terminal`. A integração 026 deve ocorrer de forma transacional ou por mecanismo durável reconciliável, evitando janela:

```text
job failed_terminal
+
DLQ intent/entry
```

Quando ambos estiverem no PostgreSQL, preferir a mesma transação. Se a captura ocorrer por processamento posterior, deve existir job reconciliador idempotente capaz de detectar terminal sem DLQ correspondente.

## Segurança e multi-tenancy

### Tenant-scoped

RLS obrigatório:

```text
USING      tenant_id = security.current_tenant_id()
WITH CHECK tenant_id = security.current_tenant_id()
```

A API não aceita `tenant_id` do body como origem de autoridade. Tenant vem do contexto autenticado/autorizado.

### System-scoped

Acesso somente por capability estreita e role explicitamente autorizada. Não conceder `BYPASSRLS` para simplificar leitura cross-tenant.

### Dados sensíveis

Proibido persistir/expor em snapshot/metadata/logs:

```text
password
access token
refresh token
API key
cookie/session
Authorization header
DATABASE_URL / broker URL com credencial
private key
stack trace com secrets
payload pessoal não necessário
```

Erro público/operacional usa códigos estáveis da fase 021; mensagem arbitrária do provider não vira dado pesquisável sem sanitização.

## RBAC

Permissões mínimas previstas no catálogo:

```text
dlq.read
dlq.reprocess
dlq.resolve
dlq.discard
```

Escopo organizacional continua aplicável. `dlq.reprocess`, `resolve` e `discard` são mutações críticas e exigem autorização no backend.

Para system entries, usar permissão/plano administrativo separado quando o modelo vigente de RBAC exigir; não conceder implicitamente a administradores tenant.

## Auditoria

Ações humanas devem registrar no Audit Trail 017:

```text
resource_type = dlq_entry
resource_id
operation
actor_user_id
membership/tenant context
request/correlation id
before status
new status
decision/reason code
```

Não incluir snapshot completo nem erro bruto na auditoria.

A captura automática em quarentena deve gerar evento operacional observável e, quando o contrato de Audit vigente exigir, trilha system actor minimizada.

## Concorrência

Reprocessamento usa claim token/lease:

```sql
UPDATE ...
SET status = 'reprocessing',
    reprocess_claim_token = $token,
    reprocess_claimed_at = clock_timestamp(),
    reprocess_claim_expires_at = clock_timestamp() + $ttl
WHERE id = $id
  AND status = 'reprocess_pending'
  AND reprocess_count < max_reprocess_attempts
RETURNING ...;
```

A conclusão exige o mesmo claim token. Lease expirado pode ser recuperado com incremento/controle de tentativa conforme política.

Também usar `version`/optimistic concurrency nas ações administrativas para evitar lost update.

## Idempotência

### Ingestão

Chave lógica:

```text
scope + source_kind + source_id
```

Inserção repetida retorna a mesma entrada existente sem duplicação.

### Solicitação de reprocessamento

Operação HTTP/API deve exigir `Idempotency-Key` usando o framework 022. A mesma intenção replayada retorna o mesmo resultado.

### Efeito externo

Publisher/handler continua responsável por dedupe da intenção lógica. DLQ não converte at-least-once em exactly-once.

## APIs administrativas previstas

Versão inicial, sujeita aos padrões HTTP vigentes:

```text
GET  /api/v1/dlq/entries
GET  /api/v1/dlq/entries/{id}
POST /api/v1/dlq/entries/{id}/reprocess
POST /api/v1/dlq/entries/{id}/resolve
POST /api/v1/dlq/entries/{id}/discard
```

Requisitos:

- autenticação obrigatória;
- RBAC backend;
- tenant/scoping backend;
- paginação cursor-based quando aderente ao padrão vigente;
- filtros allowlisted (`status`, `source_kind`, `source_type`, intervalo temporal);
- ordenação allowlisted;
- `Idempotency-Key` obrigatória nas mutações;
- Problem Details 021;
- version/precondition para mutações concorrentes;
- nunca retornar snapshot sensível bruto;
- nenhuma edição de payload.

System entries podem possuir superfície separada/interna para não misturar tenant admin com operação de plataforma.

## Retenção

A fase 026 define política e campos necessários, mas cleanup físico recorrente deve reutilizar Jobs 025.

Defaults devem ser configuráveis por tenant/plataforma onde apropriado, com limites seguros. Registros não devem ser apagados imediatamente após resolução quando ainda forem necessários para auditoria/reconciliação.

Soft delete não substitui estados `resolved/discarded`. Qualquer purge definitivo futuro deve respeitar LGPD, retenção operacional e auditoria.
